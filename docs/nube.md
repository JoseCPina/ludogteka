# Trabajo en la nube y despliegue: detalle

> Movido desde CLAUDE.md el 17 de octubre de 2026 sin cambios de contenido. Cuándo leerlo: Antes de trabajar o desplegar desde una sesión de claude.ai/code, o si el build de Vercel falla.

- **Arranque**: el campo "Setup script" del entorno corre `bash scripts/nube/preparar-entorno.sh` (Node 22+, `npm ci` —trae el CLI de Supabase—, CLI de Vercel, `gh` —versión fija bajada del release de GitHub y verificada con su checksum, porque el proxy niega `api.github.com/…/latest`—, Chromium de Playwright con sus librerías, `.env.local` de DESARROLLO escrito desde las variables, y el CLI de Supabase ligado a desarrollo). Como el setup se guarda en caché, el hook SessionStart de `.claude/settings.json` (`scripts/nube/sesion.mjs`) lo vuelve a correr en cada sesión de la nube (solo con `CLAUDE_CODE_REMOTE=true`; en la computadora del dueño no hace nada). Es idempotente. El script se niega a escribir `.env.local` si `NEXT_PUBLIC_SUPABASE_URL` no es el proyecto de desarrollo: las llaves de producción siguen viviendo solo en Vercel.
- **Qué se corre ahí, igual que en local**: `npx tsc --noEmit`, `npx eslint`, `npm run build` (+ `npm run start -- -p 3001` para lo que solo se ve compilado), `npm run dev`, `npx supabase migration new <nombre>` para crear la migración, todas las auditorías de `scripts/auditoria/` (leen `.env.local`, que el arranque dejó con las llaves de desarrollo), las siembras (`scripts/demo/sembrar-demo.mjs`, con `--prod` lee la llave de producción al vuelo por el CLI con `SUPABASE_ACCESS_TOKEN`), `scripts/plataforma/agregar-admin.mjs`, la Stripe CLI (`stripe listen`, para el cobro en modo prueba; la instala el arranque con versión fija) y Playwright (`prueba-gratis-dev.mjs`, `cobro-stripe-dev.mjs`, `scripts/demo/capturas.mjs`, el MCP; el arranque mete el certificado del proxy de la sesión en el almacén NSS de Chromium, sin eso Stripe Checkout da ERR_CERT_AUTHORITY_INVALID): el navegador se abre SIEMPRE con `abrirNavegador()` de `scripts/lib/navegador.mjs`, nunca con una ruta de Windows escrita a mano. `<slug>.localhost` lo resuelve Chromium solo; desde Node se pega a 127.0.0.1 con el `Host` puesto (como `paginas-dev.mjs`).
- **`npm run desplegar` en la nube** (`scripts/desplegar-produccion.mjs` con `CLAUDE_CODE_REMOTE=true`), mismas garantías que en local más estas:
  - **Base por la API de gestión** (`scripts/nube/migraciones-api.mjs`, el motor de `migrar-dev.mjs`: mismo formato que el CLI, una transacción por migración con su registro, se detiene al primer error de SQL; solo un fallo de red o del servidor se reintenta, sobre lo que la base diga que sigue pendiente). Producción solo se abre con `{ produccion: true }`, que pasa únicamente el script de despliegue; `migrar-dev.mjs` se sigue negando a producción. **Esto es una excepción autorizada por el dueño a "nada de SQL por la API contra producción": solo para aplicar migraciones versionadas del repo por este script, nunca SQL suelto.**
  - **Respaldo antes de migrar**: exige un respaldo físico COMPLETO de menos de 26 h (`GET /v1/projects/<ref>/database/backups`; restaurable con `…/backups/restore`) — la API no deja crear un punto de restauración al momento («endpoint unavailable», comprobado el 28 de septiembre) — y guarda una copia JSON de todas las tablas de `public` en la carpeta temporal del contenedor (dura lo que la sesión; el restaurable es el físico).
  - **Conteos de todas las tablas antes y después** (dice cuáles cambiaron) y **`auditoria_frontera()` al final: si no sale vacía, el código no se publica.**
  - **El código se publica por la API REST de GitHub** (el GraphQL de `gh pr` lo niega el proxy): antes de migrar se empuja la rama, se abre o se reusa su PR a `main` y se comprueba que se puede fusionar; después de migrar y verificar, `PUT /pulls/<n>/merge` fijado al commit revisado (si alguien empujó otra cosa, GitHub lo rechaza). Vercel construye porque `main` cambió; el script espera el build con `vercel ls` (usa `VERCEL_TOKEN`).
  - **El `fetch` de Node no pasa por el proxy de la sesión** si no se le dice, y la credencial de `GH_TOKEN` solo vale pasando por él (directo da 401): el script se relanza solo con `NODE_USE_ENV_PROXY=1`. Cualquier script nuevo que llame a GitHub desde Node en la nube va igual.
- **`scripts/nube/migrar-dev.mjs`: excepción autorizada por el dueño a "nada de SQL manual", SOLO para desarrollo.** Aplica las pendientes por HTTPS con la API de gestión (`/v1/projects/sgfolltpvktbsiisfuzq/database/query`, corre como `postgres`) con el motor compartido: compara contra `supabase_migrations.schema_migrations`, se detiene si la base tiene una versión que el repo no (igual que el CLI) o si hay una pendiente más vieja que la última aplicada (salvo `--incluir-todas`, el `--include-all`), aplica en orden cada una en UNA transacción junto con su registro (`version`, `name`, `statements` partidas igual que el CLI por `scripts/nube/sentencias.mjs`), y si una falla se deshace, no se registra y no sigue. Al final corre `auditoria_frontera()`. Se niega si algo apunta a producción o si el CLI está ligado a otro proyecto. `--comparar` comprueba que las sentencias que el CLI ya registró son idénticas a las que registraría el motor (el 28 de septiembre: 211 de 211; las aplicadas desde Windows difieren solo en CRLF, que no cuenta). Una migración con su propio `begin`/`commit` se rechaza.
## Cuando el build de Vercel falla por infraestructura (10 de octubre de 2026)
- El 10 de octubre un despliegue murió con `git_info_fail` sin que el código tuviera nada: `npm run desplegar` lo trataba como un fallo del despliegue y se salía **sin marcar los videos**. Ahora, si el build termina en Error: (1) lee el `errorCode`/`errorMessage` del deployment por la API de Vercel; si es de CÓDIGO (el build no compiló) **no reintenta** y aborta; (2) si no lo parece, lo reintenta (`redeploy` por la API) y, si sigue fallando, **crea el deployment por la API desde el commit fusionado de `main`**; (3) pase lo que pase, **siempre corre los pasos posteriores** (`sincronizar.mjs --prod` y `marcar.mjs --prod`) y, si alguno falla, imprime PENDIENTE con el comando exacto. Sale con código 1 solo si el build no quedó Ready después de todo eso.
- A mano (si el script no llegó): `node scripts/tutoriales/sincronizar.mjs --prod`, luego `node scripts/tutoriales/marcar.mjs --archivo <json> --prod`; el deployment por la API es `POST /v13/deployments?forceNew=1` con `gitSource {type: github, repoId, ref: main, sha}` y `target: production` (token en `VERCEL_TOKEN`, equipo en `.vercel/project.json`).
- **Migraciones de los dos carriles en desarrollo**: si la base de desarrollo ya tiene una migración de la PC (`…50xx00`) que todavía no está en el repo, `migrar-dev.mjs` se detiene; se reconstruye su archivo local desde `supabase_migrations.schema_migrations`, se EXCLUYE de git (`.git/info/exclude`), se aplica lo propio con `--incluir-todas` y **se borra ese archivo antes de `npm run desplegar`** (producción solo recibe lo que llegó a `main`).
