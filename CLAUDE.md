\# Ludogteka



App interna + portal de clientes para un negocio canino en San Luis Potosí (guardería, hotel, estética).



\## Contexto completo

Antes de trabajar, lee docs/PROYECTO.md: ahí está el detalle de roles, roadmap por fases, reglas de negocio y qué está fuera de alcance.



\## Stack

\- Next.js 16 (App Router, TypeScript, Tailwind), carpeta src/

\- Supabase (Auth, Postgres con RLS, Storage)

\- Esquema por migraciones versionadas: npx supabase migration new <nombre> -> editar .sql -> npx supabase db push

\- Dev en puerto 3001

Nunca se escribe una migración directo contra producción.

El script hace la verificación de datos de arriba, corre el dry-run, aplica las migraciones con reintentos, comprueba que quedaron registradas en la base y SOLO ENTONCES empuja el código. Correrlo primero con `--revisar` (no escribe nada). La cadena de conexión vive en `C:\proyectos\.ludogteka-prod-db` — FUERA del repo, una sola línea con la cadena completa, permanente: \*\*NO se borra al terminar\*\* (decisión del 21 de septiembre de 2026; ya se había dado una vez y se borró, y eso obligó a volver a pedirla). El script la lee de ahí; `LUDOGTEKA_PROD_DB_URL` sigue teniendo prioridad si viene puesta. Nunca se copia al repo, a `.env.local` ni a un mensaje. \*\*El push del código jamás se encadena a la migración con `;`\*\* — en Fase 11 así fue y el `git push` salió con el `db push` fallado: quedó código nuevo empujado contra esquema viejo, y solo no rompió nada porque el build tardó más que el reintento.

\- \*\*Las pruebas nunca se hacen en Ludogteka\*\* (29 de septiembre de 2026): ni con las cuentas de su personal ni con su terminal. Una prueba de cobro con Mercado Pago en vivo hecha en Ludogteka el 28 de septiembre dejó cobros, un gasto de comisión, una cita finalizada y un saldo en su caja y sus reportes, y hubo que limpiarla con una migración documentada (`docs/OPERACIONES-PRODUCCION.md`). Para probar el flujo: un negocio de prueba (en desarrollo, Huellitas con `negocio-prueba-dev.mjs`; en producción, uno dado de alta desde `/plataforma` con su propio admin), que cobra en simulación mientras no conecte cuenta. Para probar con dinero real: ese negocio de prueba conectado por OAuth a una cuenta de Mercado Pago que NO sea la de Ludogteka (una cuenta conecta un solo negocio), y al terminar se reembolsa en Mercado Pago y se registra la devolución en su caja.

\- \*\*Nunca a mano en producción\*\*: nada de SQL manual por consola/dashboard para cambios de esquema (eso es una migración, sin excepción) ni para cargar datos de negocio reales (tarifas, plantilla de contrato, catálogo de insumos, altas de clientes) — esos se capturan por la UI de la app, igual que los va a capturar el negocio en el día a día. La única SQL manual tolerada en producción es de un administrador de la app resolviendo un caso operativo puntual (nunca cambios de esquema), y siempre documentando qué y por qué.

\- \*\*Leer producción sin la contraseña de Postgres\*\*: la cadena de conexión no está en esta máquina a propósito y no hace falta pedirla para VERIFICAR. El CLI de Supabase tiene sesión (token en el Administrador de credenciales de Windows, no en archivo): `node node_modules/supabase/dist/supabase.js projects api-keys --project-ref xdsxjhytggpsgrmfuuff -o json` devuelve las llaves de la API REST, y con la de `service_role` se leen los conteos reales sin escribir nada. OJO: la llave `sb_secret_` que devuelve esa API viene TRUNCADA (41 caracteres) y da `401 Invalid API key`; la que sirve es la `service_role` de tipo `legacy` (JWT). Y ese 401 se disfraza de "la columna no existe" si una sonda por columna solo mira si la petición falló: hay que distinguir el código de estado, o se dan por pendientes migraciones que ya están aplicadas (pasó el 21 de septiembre de 2026). La llave nunca se imprime ni se guarda: se lee al vuelo dentro del script y se usa ahí. Para ESCRIBIR (migrar) va siempre el script de despliegue: en local con `LUDOGTEKA_PROD_DB_URL`, y en la nube por la API de gestión con el motor de migraciones (excepción autorizada el 28 de septiembre de 2026, ver «Trabajar en la nube»). Fuera de ese script, correr SQL por la API de gestión contra producción sigue siendo SQL manual, prohibido arriba.



\## Trabajar en la nube (Claude Code en claude.ai/code)

Desde el 27 de septiembre de 2026 el trabajo de PeluDesk también corre en sesiones de la nube, que clonan el repo de GitHub y no tienen nada de la computadora del dueño (ni `.env.local`, ni `C:\proyectos\.ludogteka-prod-db`, ni sesiones de CLI guardadas). Todo lo que necesitan llega por las **variables de entorno del entorno** en claude.ai/code; ningún valor vive en el repo.

- **Arranque**: el campo "Setup script" del entorno corre `bash scripts/nube/preparar-entorno.sh` (Node 22+, `npm ci` —trae el CLI de Supabase—, CLI de Vercel, `gh` —versión fija bajada del release de GitHub y verificada con su checksum, porque el proxy niega `api.github.com/…/latest`—, Chromium de Playwright con sus librerías, `.env.local` de DESARROLLO escrito desde las variables, y el CLI de Supabase ligado a desarrollo). Como el setup se guarda en caché, el hook SessionStart de `.claude/settings.json` (`scripts/nube/sesion.mjs`) lo vuelve a correr en cada sesión de la nube (solo con `CLAUDE_CODE_REMOTE=true`; en la computadora del dueño no hace nada). Es idempotente. El script se niega a escribir `.env.local` si `NEXT_PUBLIC_SUPABASE_URL` no es el proyecto de desarrollo: las llaves de producción siguen viviendo solo en Vercel.
- **Primero, comprobar el entorno**: `node scripts/nube/verificar-entorno.mjs` (sin escribir nada ni imprimir secretos): variables, REST y API de gestión de desarrollo, API y REST de producción por el CLI, Vercel y Playwright. Si algo sale ✘, se arregla eso antes de trabajar. En la nube, Postgres de desarrollo y de producción y `gh auth status` salen como `·` (informativo, no falla): el proxy de la sesión solo deja pasar HTTPS y niega TCP a 5432/6543 y el GraphQL de GitHub (comprobado el 27 de septiembre de 2026); por eso las migraciones van por la API de gestión y la fusión a `main` por la API REST de GitHub. `SUPABASE_DB_PASSWORD` y `LUDOGTEKA_PROD_DB_URL` no hacen falta ahí.
- **Qué se corre ahí, igual que en local**: `npx tsc --noEmit`, `npx eslint`, `npm run build` (+ `npm run start -- -p 3001` para lo que solo se ve compilado), `npm run dev`, `npx supabase migration new <nombre>` para crear la migración, todas las auditorías de `scripts/auditoria/` (leen `.env.local`, que el arranque dejó con las llaves de desarrollo), las siembras (`scripts/demo/sembrar-demo.mjs`, con `--prod` lee la llave de producción al vuelo por el CLI con `SUPABASE_ACCESS_TOKEN`), `scripts/plataforma/agregar-admin.mjs`, la Stripe CLI (`stripe listen`, para el cobro en modo prueba; la instala el arranque con versión fija) y Playwright (`prueba-gratis-dev.mjs`, `cobro-stripe-dev.mjs`, `scripts/demo/capturas.mjs`, el MCP; el arranque mete el certificado del proxy de la sesión en el almacén NSS de Chromium, sin eso Stripe Checkout da ERR_CERT_AUTHORITY_INVALID): el navegador se abre SIEMPRE con `abrirNavegador()` de `scripts/lib/navegador.mjs`, nunca con una ruta de Windows escrita a mano. `<slug>.localhost` lo resuelve Chromium solo; desde Node se pega a 127.0.0.1 con el `Host` puesto (como `paginas-dev.mjs`).
- **Git en la nube solo empuja la rama de la sesión**, nunca `main` directo. Los commits se hacen ahí; a `main` llega por la fusión del PR que hace `npm run desplegar -- --aplicar`.
- **Todo se hace en la nube, sin pasos en la computadora del dueño** (28 de septiembre de 2026, pedido del dueño; reemplaza el reparto nube/computadora del 27). El ciclo: 1) el trabajo se hace en la rama de la sesión (`claude/<nombre>`) y se prueba; 2) desarrollo se migra con `node scripts/nube/migrar-dev.mjs --aplicar`; 3) se commitea y se empuja la rama; 4) se despliega con `npm run desplegar -- --revisar` y luego `-- --aplicar`, **desde la misma sesión**. Si algo no se alcanza por el camino de siempre, el agente busca la vía permitida y la documenta aquí. La regla de "commits, migración a producción y despliegue los hace el agente" aplica completa en la nube.
- **`npm run desplegar` en la nube** (`scripts/desplegar-produccion.mjs` con `CLAUDE_CODE_REMOTE=true`), mismas garantías que en local más estas:
  - **Base por la API de gestión** (`scripts/nube/migraciones-api.mjs`, el motor de `migrar-dev.mjs`: mismo formato que el CLI, una transacción por migración con su registro, se detiene al primer error de SQL; solo un fallo de red o del servidor se reintenta, sobre lo que la base diga que sigue pendiente). Producción solo se abre con `{ produccion: true }`, que pasa únicamente el script de despliegue; `migrar-dev.mjs` se sigue negando a producción. **Esto es una excepción autorizada por el dueño a "nada de SQL por la API contra producción": solo para aplicar migraciones versionadas del repo por este script, nunca SQL suelto.**
  - **Respaldo antes de migrar**: exige un respaldo físico COMPLETO de menos de 26 h (`GET /v1/projects/<ref>/database/backups`; restaurable con `…/backups/restore`) — la API no deja crear un punto de restauración al momento («endpoint unavailable», comprobado el 28 de septiembre) — y guarda una copia JSON de todas las tablas de `public` en la carpeta temporal del contenedor (dura lo que la sesión; el restaurable es el físico).
  - **Conteos de todas las tablas antes y después** (dice cuáles cambiaron) y **`auditoria_frontera()` al final: si no sale vacía, el código no se publica.**
  - **El código se publica por la API REST de GitHub** (el GraphQL de `gh pr` lo niega el proxy): antes de migrar se empuja la rama, se abre o se reusa su PR a `main` y se comprueba que se puede fusionar; después de migrar y verificar, `PUT /pulls/<n>/merge` fijado al commit revisado (si alguien empujó otra cosa, GitHub lo rechaza). Vercel construye porque `main` cambió; el script espera el build con `vercel ls` (usa `VERCEL_TOKEN`).
  - **El `fetch` de Node no pasa por el proxy de la sesión** si no se le dice, y la credencial de `GH_TOKEN` solo vale pasando por él (directo da 401): el script se relanza solo con `NODE_USE_ENV_PROXY=1`. Cualquier script nuevo que llame a GitHub desde Node en la nube va igual.
- **`scripts/nube/migrar-dev.mjs`: excepción autorizada por el dueño a "nada de SQL manual", SOLO para desarrollo.** Aplica las pendientes por HTTPS con la API de gestión (`/v1/projects/sgfolltpvktbsiisfuzq/database/query`, corre como `postgres`) con el motor compartido: compara contra `supabase_migrations.schema_migrations`, se detiene si la base tiene una versión que el repo no (igual que el CLI) o si hay una pendiente más vieja que la última aplicada (salvo `--incluir-todas`, el `--include-all`), aplica en orden cada una en UNA transacción junto con su registro (`version`, `name`, `statements` partidas igual que el CLI por `scripts/nube/sentencias.mjs`), y si una falla se deshace, no se registra y no sigue. Al final corre `auditoria_frontera()`. Se niega si algo apunta a producción o si el CLI está ligado a otro proyecto. `--comparar` comprueba que las sentencias que el CLI ya registró son idénticas a las que registraría el motor (el 28 de septiembre: 211 de 211; las aplicadas desde Windows difieren solo en CRLF, que no cuenta). Una migración con su propio `begin`/`commit` se rechaza.
- **Nunca** se imprime, se copia a un archivo versionado ni se pone en un mensaje el valor de una variable del entorno. `.env.local` y `.vercel/` que genera el arranque están en `.gitignore`.



\## Reglas

- **Los resultados al dueño van en formato para copiar** (28 de septiembre de 2026, pedido del dueño, para todo: nube y computadora, cualquier tarea): el reporte final de cada respuesta va dentro de UN bloque de código (```), en texto plano con encabezados en MAYÚSCULAS y guiones, listo para copiar y pegar. Adentro va todo lo que el dueño tiene que saber o hacer (qué quedó, pruebas, pendientes, migraciones para producción, variables, comandos). Fuera del bloque, cuando mucho una línea.

\- \*\*Commits, migración a producción y despliegue los hace el agente, siempre, sin esperar a que se le pida.\*\* Acordado y reafirmado el 21 de septiembre de 2026. Cuando sus propios controles pasan (migración probada en desarrollo por REST, `tsc` y `eslint` limpios), commitea, corre `npm run desplegar -- --revisar`, y si el estado real de la base cuadra con lo esperado, `-- --aplicar`. No se le pasan comandos al usuario para que los corra él; se corren y se reporta el resultado. Lo único que detiene esa cadena es un control que no pasa o un conteo de producción que no cuadra — y entonces se para y se reporta, no se pregunta "¿procedo?".

\- \*\*Nada espera al servidor sin tope ni spinner.\*\* Todo botón que llame a una server action usa `useEspera()` (`src/hooks/use-espera.ts`): `const envio = useEspera(); const res = await envio.ejecutar(() => accion(...)); if (res.error) ...` y `<Button cargando={envio.cargando}>`. Flujos de varios pasos (subir a Storage) usan `envio.correr(...)`; formularios con `useActionState` envuelven la acción con `useAccionConTope`; un `fetch` de cliente lleva `AbortSignal.timeout(TOPE_MS)`. Nunca `const [x, setX] = useState(false)` + `setX(true)` + `await` + `setX(false)`: así estuvieron 51 botones colgándose para siempre cuando la acción tronaba (23 de septiembre de 2026). El spinner es de `Button cargando`, no un texto quieto.

\- \*\*Todo formulario termina en `<AccionesFormulario error={…} exito={…}>` con sus botones adentro\*\* (`src/components/ui/acciones-formulario.tsx`): la confirmación y el error se ven junto al botón que se apretó, no solo en el encabezado — en un formulario largo el aviso de arriba queda fuera de la pantalla y el usuario vuelve a apretar (23 de septiembre de 2026). El `<Alert>` de arriba se conserva.

\- \*\*Todo link, código o contraseña que se le pase a alguien se muestra con `CampoCopiable`\*\* (`src/components/ui/campo-copiable.tsx`): campo de solo lectura + botón de copiar con "Copiado" visible, respaldo que selecciona el texto si el portapapeles falla, y clic en el campo selecciona todo. Nunca un `<p>` con el link ni un `navigator.clipboard` a mano en el componente.

\- \*\*Un archivo `"use server"` solo exporta funciones async.\*\* Nada de `export type { X }` (re-exportar un tipo importado), `export const`, ni `export {}` de otro módulo. El build de producción de Next deja el re-export como un export en tiempo de ejecución de un nombre que TypeScript ya borró y el módulo entero truena al cargarse (`ReferenceError: MetodoPago is not defined`), con él TODA server action invocada desde la página que lo importe — y en desarrollo funciona, así que no se ve hasta producción. Así estuvo rota la ficha del cliente (link de complemento, restablecer contraseña) del 29 de julio al 23 de septiembre de 2026; el síntoma era el spinner eterno y después el error genérico. Los tipos se importan de donde se definen. Cuando una server action falle en producción con el mensaje genérico, el mensaje trae la referencia (digest): se busca en `npx vercel logs <deployment>`.

- **Permisos delegables por persona** (24 de septiembre de 2026, migración `20260924025425`): admin le da a una persona de RECEPCIÓN en particular permisos extra (`permisos_staff`, pantalla `/admin/permisos`, catálogo en `src/lib/auth/permisos.ts`): costos e inventario, tarifas, reportes financieros, personal, configuración del negocio, excepciones al reservar, descuentos sin tope y plantillas de contrato. En la base, toda guardia o política de esas áreas usa `tiene_permiso('clave')` (incluye a admin), no `is_admin()`. **Nunca se delega** y sigue con `is_admin()`: dar o quitar permisos (`otorgar_permiso`/`revocar_permiso`), crear admins o cambiar roles, el tope de descuentos de recepción (`configuracion_descuentos`: dárselo a "configuración" sería "descuentos sin tope" por la puerta de atrás), devoluciones y quitar una evaluación. Los reportes son `security definer` (con la RLS de quien llama, alguien con el permiso vería números parciales de caja).
