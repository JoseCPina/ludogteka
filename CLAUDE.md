# Ludogteka / PeluDesk

App interna + portal de clientes para negocios caninos y veterinarios (guardería, hotel, estética, veterinaria). Ludogteka (San Luis Potosí) es el negocio #1 de PeluDesk, una app y una base para varios negocios. Antes de trabajar, lee docs/PROYECTO.md (roles, roadmap, reglas de negocio, fuera de alcance). Este archivo tiene solo lo que hace falta en cada sesión; el detalle por tema está en docs/ (índice al final).

## Stack y estructura
- Next.js 16 (App Router, TypeScript, Tailwind) en `src/`: `src/app` (rutas: `(staff)`, `portal`, `peludesk` = sitio de la plataforma, `plataforma`, `api`), `src/lib` (lógica por tema), `src/components`.
- Supabase (Auth, Postgres con RLS, Storage). Esquema por migraciones versionadas: `npx supabase migration new <nombre>` → editar .sql → aplicar (dev: `node scripts/nube/migrar-dev.mjs --aplicar` o `npx supabase db push`).
- Dev en puerto 3001 (`npm run dev`; lo que solo se ve compilado: `npm run build` + `npm run start -- -p 3001`).
- Controles: `npx tsc --noEmit`, `npx eslint`, `npm run secretos`, auditorías en `scripts/auditoria/` (Huellitas en desarrollo; una por una), `select * from auditoria_frontera()` vacía después de cualquier migración.
- Scripts: `scripts/desplegar-produccion.mjs` (`npm run desplegar`), `scripts/nube/`, `scripts/demo/` (demo Patitas & Co.), `scripts/tutoriales/`, `scripts/plataforma/`, `scripts/clinica-demo/`, `scripts/whatsapp/meta.mjs`, `scripts/videos/`.

Nunca se copia al repo, a `.env.local` ni a un mensaje. **El push del código jamás se encadena a la migración con `;`** — en Fase 11 así fue y el `git push` salió con el `db push` fallado: quedó código nuevo empujado contra esquema viejo, y solo no rompió nada porque el build tardó más que el reintento.

Para probar el flujo: un negocio de prueba (en desarrollo, Huellitas con `negocio-prueba-dev.mjs`; en producción, uno dado de alta desde `/plataforma` con su propio admin), que cobra en simulación mientras no conecte cuenta. - **Nunca a mano en producción**: nada de SQL manual por consola/dashboard para cambios de esquema (eso es una migración, sin excepción) ni para cargar datos de negocio reales (tarifas, plantilla de contrato, catálogo de insumos, altas de clientes) — esos se capturan por la UI de la app, igual que los va a capturar el negocio en el día a día. La única SQL manual tolerada en producción es de un administrador de la app resolviendo un caso operativo puntual (nunca cambios de esquema), y siempre documentando qué y por qué.
- **Leer producción sin la contraseña de Postgres**: la cadena de conexión no está en esta máquina a propósito y no hace falta pedirla para VERIFICAR. El CLI de Supabase tiene sesión (token en el Administrador de credenciales de Windows, no en archivo): `node node_modules/supabase/dist/supabase.js projects api-keys --project-ref xdsxjhytggpsgrmfuuff -o json` devuelve las llaves de la API REST, y con la de `service_role` se leen los conteos reales sin escribir nada. OJO: la llave `sb_secret_` que devuelve esa API viene TRUNCADA (41 caracteres) y da `401 Invalid API key`; la que sirve es la `service_role` de tipo `legacy` (JWT). Y ese 401 se disfraza de "la columna no existe" si una sonda por columna solo mira si la petición falló: hay que distinguir el código de estado, o se dan por pendientes migraciones que ya están aplicadas (pasó el 21 de septiembre de 2026). La llave nunca se imprime ni se guarda: se lee al vuelo dentro del script y se usa ahí. Para ESCRIBIR (migrar) va siempre el script de despliegue: en local con `LUDOGTEKA_PROD_DB_URL`, y en la nube por la API de gestión con el motor de migraciones (excepción autorizada el 28 de septiembre de 2026, ver «Trabajar en la nube»). Fuera de ese script, correr SQL por la API de gestión contra producción sigue siendo SQL manual, prohibido arriba.

## Trabajar en la nube (Claude Code en claude.ai/code)
Desde el 27 de septiembre de 2026 el trabajo de PeluDesk también corre en sesiones de la nube, que clonan el repo de GitHub y no tienen nada de la computadora del dueño (ni `.env.local`, ni `C:\proyectos\.ludogteka-prod-db`, ni sesiones de CLI guardadas). Todo lo que necesitan llega por las **variables de entorno del entorno** en claude.ai/code; ningún valor vive en el repo.
- **Primero, comprobar el entorno**: `node scripts/nube/verificar-entorno.mjs` (sin escribir nada ni imprimir secretos): variables, REST y API de gestión de desarrollo, API y REST de producción por el CLI, Vercel y Playwright. Si algo sale ✘, se arregla eso antes de trabajar. En la nube, Postgres de desarrollo y de producción y `gh auth status` salen como `·` (informativo, no falla): el proxy de la sesión solo deja pasar HTTPS y niega TCP a 5432/6543 y el GraphQL de GitHub (comprobado el 27 de septiembre de 2026); por eso las migraciones van por la API de gestión y la fusión a `main` por la API REST de GitHub. `SUPABASE_DB_PASSWORD` y `LUDOGTEKA_PROD_DB_URL` no hacen falta ahí.
- **Git en la nube solo empuja la rama de la sesión**, nunca `main` directo. Los commits se hacen ahí; a `main` llega por la fusión del PR que hace `npm run desplegar -- --aplicar`.
- **Todo se hace en la nube, sin pasos en la computadora del dueño** (28 de septiembre de 2026, pedido del dueño; reemplaza el reparto nube/computadora del 27). El ciclo: 1) el trabajo se hace en la rama de la sesión (`claude/<nombre>`) y se prueba; 2) desarrollo se migra con `node scripts/nube/migrar-dev.mjs --aplicar`; 3) se commitea y se empuja la rama; 4) se despliega con `npm run desplegar -- --revisar` y luego `-- --aplicar`, **desde la misma sesión**. Si algo no se alcanza por el camino de siempre, el agente busca la vía permitida y la documenta aquí. La regla de "commits, migración a producción y despliegue los hace el agente" aplica completa en la nube.
- **Nunca** se imprime, se copia a un archivo versionado ni se pone en un mensaje el valor de una variable del entorno. `.env.local` y `.vercel/` que genera el arranque están en `.gitignore`.
- Detalle (arranque, qué se corre ahí, despliegue por la API de gestión, respaldo, PR por la API REST de GitHub, `migrar-dev.mjs`, build de Vercel que falla por infraestructura): docs/nube.md.

## Secretos
- **Regla**: ninguna contraseña, par correo + contraseña, llave de API ni token se escribe en código, scripts, pruebas, semillas, CLAUDE.md ni docs. Las cuentas de prueba y de siembra nacen con `claveAleatoria()` (`scripts/lib/clave.mjs`, 24 bytes aleatorios) que nadie guarda; una prueba que teclea la clave por pantalla la genera al arrancar y la usa en memoria. Un valor que no puede ir en el repo va en una variable de entorno (Vercel / `.env.local`).
- **Cómo entran las cuentas gemelas del corredor y «Ver demo»: SIN contraseña.** El corredor de tutoriales (`scripts/tutoriales/lib/sesion.mjs`: `generateLink` magic link con la llave de servicio + `verifyOtp` → cookie del dominio del demo) y `/demo/entrar/<rol>` (`src/app/demo/entrar/[rol]/route.ts`, el mismo `generateLink` en el servidor) abren sesión por enlace mágico; ninguna cuenta del demo, del corredor (`tutoriales.*`, `demo.mvz`, `demo.mvz2`) ni de la clínica demo tiene una contraseña conocida. La PC no tiene que configurar nada nuevo: usa la misma llave de servicio de su `.env.local`.
- **Escaneo** (`scripts/seguridad/escanear-secretos.mjs`): bloquea contraseñas como literal (`password: "…"`, `.fill("…")` en un campo de contraseña, prefijos fijos con `${}`), pares correo + contraseña, llaves de Stripe (`sk_`, `whsec_`), Supabase (`sb_secret_`, JWT), Anthropic, Meta (`EAA…`), GitHub, Vercel, Slack, Google, AWS, llaves privadas, cadenas de Postgres con contraseña y literales largos asignados a `key/token/secret`. Corre (1) en el **pre-commit** (`.githooks/pre-commit`; `npm install`/`npm ci` fija `core.hooksPath` con el script `prepare`; en una máquina que ya tenía el repo, correr `npm install` una vez o `git config core.hooksPath .githooks`) y (2) en **CI** (`.github/workflows/secretos.yml`: todo lo versionado en cada push y PR). A mano: `npm run secretos`. Un falso positivo real lleva `escaner-ok: motivo` en su línea; **un valor que parece secreto nunca se «arregla» con ese comentario**.
- **Incidente del 12 de octubre de 2026** (GitGuardian, «Company Email Password», push de las 22:18 UTC con los PR #63 y #67): lo marcado fue el patrón `password: \`Corredor-${crypto.randomUUID()}\`` junto a los correos `tutoriales.*@peludesk.mx` en `scripts/demo/cuentas-corredor.mjs` (la clave real era aleatoria por cuenta, no estaba en el repo). La revisión del árbol y del historial encontró además contraseñas literales de PRUEBAS (`Prueba-12345`, `Prueba-123456`, `Prueba-Liga-2026` —esta última con la que el recorrido de la clínica demo daba de alta al cliente de ejemplo en producción—, `Audit-<sufijo>-segura`, `Aud-<sufijo>-x!`, `Plataforma-<hora>`): todas se reemplazaron por `claveAleatoria()`. **Se rotaron** las contraseñas de las 342 cuentas de desarrollo (excepto la personal del dueño) y de las 22 cuentas de la clínica demo y del demo en producción; el historial no se reescribió (con la contraseña rotada, lo viejo ya no sirve).

## Reglas de código y UI
- **Nada espera al servidor sin tope ni spinner.** Todo botón que llame a una server action usa `useEspera()` (`src/hooks/use-espera.ts`): `const envio = useEspera(); const res = await envio.ejecutar(() => accion(...)); if (res.error) ...` y `<Button cargando={envio.cargando}>`. Flujos de varios pasos (subir a Storage) usan `envio.correr(...)`; formularios con `useActionState` envuelven la acción con `useAccionConTope`; un `fetch` de cliente lleva `AbortSignal.timeout(TOPE_MS)`. Nunca `const [x, setX] = useState(false)` + `setX(true)` + `await` + `setX(false)`: así estuvieron 51 botones colgándose para siempre cuando la acción tronaba (23 de septiembre de 2026). El spinner es de `Button cargando`, no un texto quieto.
- **Todo formulario termina en `<AccionesFormulario error={…} exito={…}>` con sus botones adentro** (`src/components/ui/acciones-formulario.tsx`): la confirmación y el error se ven junto al botón que se apretó, no solo en el encabezado — en un formulario largo el aviso de arriba queda fuera de la pantalla y el usuario vuelve a apretar (23 de septiembre de 2026). El `<Alert>` de arriba se conserva.
- **Todo link, código o contraseña que se le pase a alguien se muestra con `CampoCopiable`** (`src/components/ui/campo-copiable.tsx`): campo de solo lectura + botón de copiar con "Copiado" visible, respaldo que selecciona el texto si el portapapeles falla, y clic en el campo selecciona todo. Nunca un `<p>` con el link ni un `navigator.clipboard` a mano en el componente.
- **Un archivo `"use server"` solo exporta funciones async.** Nada de `export type { X }` (re-exportar un tipo importado), `export const`, ni `export {}` de otro módulo. El build de producción de Next deja el re-export como un export en tiempo de ejecución de un nombre que TypeScript ya borró y el módulo entero truena al cargarse (`ReferenceError: MetodoPago is not defined`), con él TODA server action invocada desde la página que lo importe — y en desarrollo funciona, así que no se ve hasta producción. Así estuvo rota la ficha del cliente (link de complemento, restablecer contraseña) del 29 de julio al 23 de septiembre de 2026; el síntoma era el spinner eterno y después el error genérico. Los tipos se importan de donde se definen. Cuando una server action falle en producción con el mensaje genérico, el mensaje trae la referencia (digest): se busca en `npx vercel logs <deployment>`.
- **Una política de RLS que pregunta por quien llama va envuelta: `using ((select public.is_staff()))`**, igual `is_admin()`, `current_rol()`, `es_admin_plataforma()` y `tiene_permiso('x')` (migración `20260925190601`). Sin el `select`, Postgres la evalúa fila por fila y consulta membresías cada vez: `cuentas_abiertas()` pasaba de 8 segundos con un mes de operación y la Caja no cargaba (25 de septiembre de 2026).
- **Un guardia de rol nunca se escribe contra un valor que pueda ser NULL.** `current_rol()` devolvía NULL para un llamador anónimo, y `null not in ('admin','recepcion')` es NULL, no TRUE: el `if` no se dispara y el guardia deja pasar. Así estuvieron abiertos 39 guardias desde Fase 1 hasta que se encontró en Fase 13. Hoy `current_rol()` devuelve `'anonimo'` y `is_admin()`/`is_staff()` van con `coalesce(..., false)`, así que el idioma de siempre ya es seguro — pero cualquier guardia nuevo se prueba **también con la llave anónima pelada**, no solo con un JWT de cada rol: es el caso que ninguna prueba con sesión puede ver.
- **`revoke execute ... from public` NO le quita el permiso a `anon` en Supabase.** El proyecto trae ALTER DEFAULT PRIVILEGES que le concede EXECUTE a anon/authenticated/service_role sobre cada función nueva, y eso es una concesión directa al rol: hay que nombrar a `anon` explícitamente para revocárselo. **Y al revés: `revoke … from anon` NO quita el EXECUTE de PUBLIC** (toda función nueva lo trae): la llave anónima sigue entrando por ahí (4 de octubre de 2026: `normalizar_raza`, `razas_fuera_de_catalogo` y `razas_sin_grupo` quedaron abiertas así). ## El límite de 1,000 filas de la API de Supabase
- **Reglas**: (1) un total o un conteo sale de la base (función SQL, `count` exacto o un agregado), nunca trayendo filas para sumarlas aquí (`wa_uso_ia_resumen` suma el gasto de IA); (2) una lista que hace falta completa se lee con `leerTodo` / `leerTodoPorIds` (`src/lib/supabase/paginar.ts`; en scripts, `todas` / `contar` de `scripts/lib/paginar.mjs`), que pide de 1,000 en 1,000 y **exige ordenar con una llave única al final** (`.order("nombre").order("id")`); (3) un `.in("columna", ids)` con muchos ids va por bloques (`leerTodoPorIds`: la URL tiene tope de largo); (4) una función pesada que devuelve tabla y que se usa completa se envuelve en una que devuelve un solo `jsonb` (`cuentas_abiertas_json`: una sola cuenta de la base, sin tope; paginar `cuentas_abiertas` recalculaba la función entera en cada página y con un mes de operación pasa del `statement_timeout` de 8 s); (5) un historial largo de un solo producto enseña los últimos 500 y lo dice (`/inventario/<id>`), con la existencia calculada en la base.
- Causa, escáner, prueba con negocio desechable y rendimiento de `cuentas_abiertas`: docs/lecciones-tecnicas.md.

## PeluDesk: varios negocios en una base

  - **El negocio lo decide el dominio.** El middleware resuelve el negocio por host (`src/lib/negocio/host.ts` + RPC `negocio_por_host`: dominio propio, `<slug>.peludesk.mx`, `<slug>.localhost` en desarrollo; localhost, 127.0.0.1 y `*.vercel.app` → `NEGOCIO_POR_OMISION`), tira los `x-negocio-*` que traiga el navegador y pone los suyos, firmados (`src/lib/negocio/firma.ts`: la petición interna con la que Next pinta el destino de un `redirect()` de acción de servidor llega a localhost y sin la firma caería en el negocio por omisión).   - **El encabezado `x-negocio-id` dice DE QUÉ negocio es la petición, nunca autoriza.** `negocio_actual()` lo lee (o `app.negocio_id`); la autorización es la MEMBRESÍA de la persona en ese negocio (`membresias`: rol, cliente_id; `current_rol()`, `es_miembro()`, `mi_cliente_id()`, `tiene_permiso()` la leen). `profiles` es la persona (una cuenta de Auth por teléfono, en todos los negocios); `profiles.rol`, `profiles.cliente_id`, `profiles.sucursal_id` y `razas.grupo_raza_id` son legado, vacíos y con candado.

El webhook de Mercado Pago no trae negocio: lo saca de la orden (`contextoDeOrden`).
  - **Integraciones por negocio** (28 de septiembre de 2026, migraciones `20260928040148` y `20260928041716`): cada negocio cobra con SU cuenta y cotiza recolección con la llave de PeluDesk. Detalle en «Integraciones por negocio» (Reglas).

## Checklist: tabla nueva
Cada tabla nueva lleva esto DENTRO de su propia migración de creación, no en un ALTER aparte después — así se perdió una vez (created_by sin default en servicios/tarifas de Fase 3, corregido hasta Fase 4 porque la convención solo vivía en las tablas de Fase 2, no estaba escrita en ningún lado):
- Columnas estándar: id uuid pk default gen_random_uuid(), created_at timestamptz not null default now(), updated_at timestamptz not null (sin default, lo llena el trigger), deleted_at timestamptz.
- created_by uuid references auth.users(id) on delete set null default auth.uid() — el DEFAULT va en el propio CREATE TABLE, siempre.
- Trigger set_updated_at before insert or update on la tabla for each row execute function public.set_updated_at().
- alter table ... enable row level security, con al menos una política de SELECT y una de INSERT/UPDATE escritas explícitamente en la misma migración. Nunca dejar una tabla con RLS activado y cero políticas (bloquea todo en silencio) ni con RLS desactivado.
- Baja lógica (deleted_at), nunca DELETE, en cualquier tabla que el negocio necesite dar de baja sin perder el historial.
- PeluDesk: `negocio_id uuid not null references public.negocios(id) default public.negocio_actual()`, índice por `negocio_id`, las políticas `<tabla>_negocio` (RESTRICTIVE) y `<tabla>_negocio_definer`, `grant … to peludesk_definer`, y los índices únicos con `negocio_id` adelante (único DENTRO del negocio). Después, `auditoria_frontera()` vacía.
